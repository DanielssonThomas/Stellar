# Agent supervision

`tools/policy/supervise-worker.mjs` provides a deterministic, model-independent supervisor. It accepts Peon and Mira adapters; it never accepts or invokes a Codex worker. Its unit tests use simulated adapters. The trusted live entry point is wired separately and its live issue-to-PR trial remains gated by issue #24 and its implementation prerequisites.

## Limits and progress

Defaults per worker are two attempts, ten minutes, 64 tool calls, 32,000 reported model tokens, two repeated unchanged failures, and two attempts without worktree progress. Hard ceilings are three attempts, 15 minutes, 128 tool calls, 64,000 tokens, and three repeated or unproductive attempts. Peon and Mira each receive their own tool and token budget; task runtime is capped at twice the per-worker runtime.

Adapters must execute tools through `budget.runTool` and model requests through `budget.runModel`. The model adapter supplies its prompt token estimate and must honor the returned `maxOutputTokens`. Actual provider usage is charged when present; when usage is unavailable, the full reserved prompt and output budget is charged. The supervisor receives a trusted `inspectWorktree` callback and compares its fingerprints; model-written progress claims do not count as worktree progress. A trusted `verify` callback must return at least one passing result before the task can complete.

Restricted live adapters must also expose a trusted `usage()` poll sourced from the metering sidecar, never from Hermes' self-reported usage file. The sidecar applies the supervisor-supplied cumulative limits before forwarding model output, counts tool calls in the complete model response before releasing it to Hermes, and returns monotonic counters over its loopback-only control endpoint. The supervisor polls while the worker runs, updates its handoff counters, and cancels the worker on exhausted budgets or any usage-query failure. A live adapter without this channel is inadmissible; simulated adapters remain useful for supervisor unit tests only.

The host schedules one live poll every 100 ms without overlapping reads. Each poll checks the exact sidecar ID, start time, restart count, and running state, then reads `/usage` through a bounded asynchronous Windows–WSL–Podman call. The usage transport retains its three-second bound. A slow valid read delays the next snapshot; a timeout, stopped sidecar, malformed counters, or cancelled poll fails closed. The separate proxy `/health` check identifies an unavailable model before worker launch. Neither a health response nor an absent usage response supplies zero counters.

The trusted live entry point is `tools/policy/supervised-peon-run.mjs`. Its `runSupervisedPeonIssue` function re-fetches the issue and claim, checks owner, target, dependencies, branch, session, and immutable image before constructing the live Peon adapter. It wires that adapter into `superviseWorker` with the existing limits and one attempt, and it does not authorize automatic Mira or Codex execution. The caller must supply named verification commands from trusted configuration; the runner executes each check in a rootless container on `--network=none`, with the pinned image, read-only protected mounts, no GitHub secret, no model endpoint, and no integration credential. Do not derive verification commands from issue text or worker output.

An explicitly selected `bounded-coding` assignment additionally requires the narrow profile and a trusted task-context plan. The host re-fetches issue metadata and the develop head, verifies the registered claim worktree and the exact rootless Peon workspace revision are clean and identical, reads mandatory guidance and selected excerpts from the workspace that will be mounted, then repeats those checks before launch. The in-memory manifest is byte-limited and is not included in the supervisor handoff. It gives Hermes the issue objective, criteria, constraints, exact authorization, and relevant excerpts; the rest of the issue body is represented by a digest. The trusted host passes this packet to one Hermes process, supplies the two-completion cap to its single sidecar, and reserves that issue/session attempt atomically before container creation. Peon is directed to edit the authorized source and test paths before any broad exploration. The host performs scoped checks after Hermes exits. This edit-first instruction does not establish that Qwen will generate an edit within two requests.

The opt-in `minimal-coding` assignment uses the same issue, claim, exact-revision, meter, supervisor, and independent verification checks. The host supplies objective, acceptance criteria, selected source excerpts, and at most two selected coding skills. Hermes receives a short, trusted coding `AGENTS.md` overlay instead of the repository governance instructions; the host verifies that exact overlay in the effective system prompt before launch. The worker has the narrow coding toolset and no scripted completion count. Its model-token, tool-call, runtime, and attempt ceilings remain enforced by the host. The checkout is read-only except for validated task directories, and this path does not receive the GitHub fork token. The host still rejects changes outside those directories before running trusted verification. A worker can suggest useful coding knowledge in its final report; that report does not alter trusted skills or policy.

The 100 ms live-usage poll remains in place for this path. An event-only replacement cannot fail closed on a stalled or lost event without a separate heartbeat and timeout, so the current bounded poll is the simpler verified safety mechanism. It reads counters, not diagnostic text, and the existing tests cover timeout, malformed usage, stopped sidecar, cancellation, and final accounting.

The 2026-10-26 #50 attempt forwarded two completions (12,637 and 12,786 prompt tokens), emitted two tool calls, and reached the request limit without a changed file. The retained numeric meter records do not include tool names, arguments, execution results, or session content; the worker's Hermes home was temporary. The exact two calls and whether their underlying tools ran cannot be recovered from that attempt. Do not infer tool execution from emitted-call counts. The handoff remains `safeToResume: false` and must not be resumed.

The separate `edit-first-4` workflow is restricted to issue #50 with the explicit `narrow-evidence` profile. It fixes four forwarded completions and 52,000 cumulative model tokens while retaining one attempt, 600 seconds, 64 tool calls, the pinned image, the same sandbox, and no paid route. Its single-use host command is `node D:\ai-repositories\stellar\tools\policy\experiments\run-issue-50-edit-first-four.mjs`. It requires a newly ready issue, released claim, clean worktrees, exact current develop, intact prior handoffs, and separate authorization to execute. It claims a fresh session, fast-forwards the clean issue worktrees, checks the existing Qwen container, and starts the trusted supervisor. Do not run it during preparation.

This profile mounts a revision-checked, read-only Hermes pre/post tool hook and matching trusted meter source into the existing pinned image. The hook sends only a hashed call ID, tool name, argument count and byte size, result byte size, bounded duration, status, and numeric exit code to the attempt sidecar. The sidecar accepts only reviewed tool names and rejects extra fields and unmatched results, and the host validates the sanitized events before placing them in the handoff. A pre event means dispatch was observed; a post event records the reported execution outcome. Missing post events remain incomplete, including on cancellation. The hook runs in the restricted worker, so its events are diagnostic evidence rather than independent proof; compare them with metered emitted calls, the actual worktree diff, and isolated validation before claiming coding success. No raw arguments, output, credentials, or session text are persisted.

An offline `/tokenize` and `/apply-template` measurement with the pinned image, current Qwen tokenizer, and the small #50 source/test excerpts counted 12,309 tokens for the prior first-request packet and 10,381 for the edit-first packet. The latter uses only the mandatory implementation skill; the component generator skill is unnecessary for editing an existing atom. Fixed runtime system instructions still cost 4,669 tokens, the trusted task manifest costs 2,201, and the narrow profile's ten tool schemas cost about 2,531. These are constructed prompt measurements, not a model completion or proof that Qwen will edit. With history and tool results, a normal inspect/edit/check/final loop needs about four requests; at roughly 10–13 thousand prompt tokens each plus bounded output, a proposed ceiling is four forwarded requests and 52,000 total model tokens, within the existing 64,000 hard token ceiling. The #50 opt-in activates those bounds only when the separately authorized single-use experiment starts; the ordinary bounded workflow still enforces two requests and 32,000 tokens.

## Handoffs and recovery

Pass an absolute `handoffPath` to persist the issue number, owner, authorized target, branch, worktree, attempts, file changes, attempted solutions, verification results, and failure evidence after every attempt. Worker stdout and stderr are captured only as bounded in-memory tails; sensitive values are redacted before sanitized excerpts enter the trusted local handoff. Raw process streams are never printed or published. `readHandoff` loads that record for a resume. A resume must keep the same issue, target branch, issue branch, and worktree path. Interruption pauses the task and retains the current worker for recovery.

For a stopped Peon apprenticeship attempt, the trusted host may call `appendMentorFeedback` with the handoff's expected update time and recorded worktree fingerprint. It rechecks the worktree, cites an actual recorded failure or failed verification from the latest attempt, and appends at most twelve short mentor events. Each event records its supervisor revision, execution owner, issue owner, and attempt count. Levels are diagnostic, conceptual guidance, and Codex fix; a Codex fix is attributed to Codex. Optional lesson text is marked `draft` in the handoff and has no effect on active skills. A feedback event never starts another attempt. Promote a lesson only after Codex verifies the incident and its reuse scope, through a reviewed repository change.

A correction packet may consume mentor feedback only when its provenance is valid for the authorized execution and its source-state assumptions remain current at the trusted use boundary. Await `correctionFeedbackFromHandoff({ handoffPath, issueNumber, inspectWorktree })` using the same trusted inspector as supervision. It reads the authoritative handoff under the shared lock and returns a process-local, immutable feedback handle. It rejects completed or unsafe handoffs, Codex-fix events, missing or altered evidence, subsequent executions (even with identical output), and changed workspace contents. Historical events remain untouched. Legacy events without execution provenance cannot authorize correction; the host must freshly accept feedback for an eligible current attempt.

Pass that handle as `contextPlan.mentorFeedback` to the trusted `runSupervisedPeonIssue` entry point with a distinct destination handoff. It holds the source handoff lock throughout preparation and consumption, rechecks provenance and contents before constructing the packet and after preparation, and checks the current issue/claim and source again immediately before the adapter runs. Standalone packet construction must use `withCurrentCorrectionFeedback(handle, { issueNumber }, prepare, consume)`; `prepare` builds the packet, and `consume` uses it only after the final check. Serialized, copied, expired, or unguarded feedback cannot enter the synchronous minimal-context builder. The callback's `assertCurrent(task)` also binds the source to the full trusted assignment. The source lock coordinates cooperating supervisors, not arbitrary filesystem writers: the host must retain the existing exclusive workspace/claim isolation throughout use. A crashed holder fails closed and requires operator recovery of the abandoned lock.

These APIs do not grant another attempt. The clean exact-develop workspace requirements, single-use revision reservation, owner/claim checks, model/tool/runtime limits, and separate execution authorization still apply. Reusing a failed dirty workspace or an already consumed minimal-coding revision remains denied. Do not count a Codex-written repair as independent Peon success.

Immediately before a separately authorized correction dispatch, the guarded consumer records `correctionUse` with its destination handoff and feedback digest, advances the source revision, and marks the source `superseded`. This preserves the event history while preventing reuse or resume of the old source, including after a correction with identical output. A failed or interrupted dispatch does not roll this transition back. Standalone execution consumers must call the preparation callback's second argument, `consumeExecution(task, authorizedWorkspace)`, before dispatch; ordinary packet previews do not consume an attempt. The production entry point performs this transition automatically within the retained lock.

Supervisor and mentor handoff writes use the same bounded file lock. Each supervisor save advances a persisted revision and validates the execution owner; a resumed supervisor claims the stopped handoff before tier authorization or worker execution. Legacy stopped handoffs without these fields can be claimed once under the lock. A stale supervisor cannot replace an active state. A supervisor save retains mentor events accepted from an older snapshot. Diagnostic feedback uses a sanitized UTF-8-byte-bounded excerpt of the trusted failure or verification summary while retaining the cited handoff evidence fingerprint. The stopped attempt fingerprint is captured after confirmed verification termination, while the worker-output fingerprint remains available separately for progress accounting.

The production inspector uses NUL-delimited Git path records and fingerprints tracked diff evidence together with content digests and file identity/type for all changed paths, including untracked files. Its trusted Python helper is supplied by the host over stdin; it follows no symlink components, rejects special files and hard links, and checks descriptor identity before and after reading. A separate directory-entry type check catches special files that Git silently omits, pruning `.git` and Git-ignored directories without reading their contents. Two complete snapshots must match. Inspection is bounded to 100 changed paths, 100,000 directory entries and 64 directory levels per snapshot, 8 MiB per file/Git output, 32 MiB of file reads per snapshot, and a shared 15-second deadline; missing tools, inconsistent snapshots, invalid UTF-8 names, or exceeded bounds fail closed. Only the final digest and existing changed-path metadata leave the inspector, never file contents. The new fingerprint format deliberately invalidates older content-incomplete fingerprints for mentor use; it does not rewrite historical handoffs or expand writable paths.

Worker adapters must implement `cancel(reason)` and return `true` only after the worker process has stopped. If timeout or interruption cannot confirm termination, the supervisor marks the handoff unsafe to resume and will not transfer the worktree. Verification callbacks need the same `cancel` contract when they can outlive their deadline. Only a trusted host that independently confirms termination may resume such a handoff with `confirmPreviousWorkerStopped: true`.

Peon cancellation confirmation uses a 4.5-second shared deadline inside the supervisor's 5-second cancellation grace. It scopes lifecycle inspection to the exact `stellar-peon-worker-<issue>-<attempt>`, `stellar-peon-meter-<issue>-<attempt>`, or `stellar-peon-verify-<issue>-<attempt>` name in Peon's rootless Podman store. A targeted `podman ps --all` inspection treats a missing container (including `--rm` removal) or a known non-running state as confirmed only after the corresponding launch operation has settled. The `podman stop` exit status is advisory; a fresh lifecycle read decides. Worker final usage is read before the metering sidecar is stopped, and both containers must be absent or terminal before the adapter reports cleanup complete. Concurrent repeat cancellations share the same confirmation promise.

Podman/WSL errors, malformed lifecycle output, a still-running worker or sidecar, or an expired deadline remain inconclusive. In those cases the supervisor records cancellation as unconfirmed, keeps `safeToResume: false`, and does not transfer or resume the worktree. A trusted operator must independently establish that both attempt containers have stopped before explicitly confirming a resume. These checks never query or stop the persistent Qwen container or containers from another attempt.

When cancellation is unconfirmed, the handoff keeps the primary stop cause separately from the secondary `CancellationUnconfirmed` failure. Known supervisor causes use bounded values such as `model-tokens-budget-exhausted`, `usage-accounting-failed`, or `runtime-budget-exhausted`; unclassified causes are recorded as `unknown`. This evidence does not make the worktree resumable. Existing handoffs are not rewritten.

New handoffs also preserve the sanitized initiating usage category, phase, and bounded elapsed time when cancellation is unconfirmed. The 2026-10-26 #50 handoff predates that field and cannot establish its exact initiating category. Retained Podman events place that failure in startup readiness: the meter ran, but the worker was never created. Qwen had exited before the attempt. Windows and WSL records show a host power-off and WSL shutdown on 2026-10-25, immediately followed by Qwen's second-interrupt message, CUDA error, and exit 139. Those records do not identify a separate memory-exhaustion cause, and the exact historical meter response was not retained.

When Peon reaches a deterministic stop condition, the supervisor calls `authorizeHandoff`. The trusted host callback must transfer the issue claim to `worker:mira` with the existing issue worktree manager and return the verified owner, target branch, branch, and path. If authorization is absent or differs, the supervisor leaves a resumable `handoff-pending` record and does not start Mira.

If Mira reaches a stop condition, the returned escalation request asks to mark the issue `blocked` for `agent-capability`, includes the handoff evidence, and sets `invoked: false`. The host may provide `recordEscalationRequest` to use the existing `update-issue` workflow with `formatCapabilityBlockerComment`; the callback must only write the issue update and return `true` after confirmation. Without that callback, the request stays in the handoff with `recorded: false`. Neither path launches Codex or consumes paid usage.

These callbacks are integration boundaries, not security controls. The caller must validate current issue ownership and use separately enforced worker permissions and OS isolation before starting a live adapter.
