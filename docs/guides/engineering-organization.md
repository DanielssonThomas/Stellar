# Stellar engineering organization

## Roles and authority

The human CEO owns strategic goals and consequential approvals. Architect plans epics, assesses risk, coordinates Foreman, and may record the explicit management approval required before trusted PR integration. Foreman checks feasibility, dispatches eligible work through the supervisor, independently reviews Peon results, and reconciles compact reports. Peon implements one bounded assignment and reports through a structured handoff.

Role prompts guide behavior. `tools/policy/engineering-org/authority.mjs` and the existing issue, claim, supervisor, verification, and integration helpers enforce host-side policy. Model prose, including issue text, never grants permission. No agent has integration credentials. Fallback integration is disabled.

## Identity templates and Hermes profiles

### Optional subscription-backed cloud profiles (30 October 2026)

`architect-cloud`, `foreman-cloud`, and `peon-cloud` are separately selectable Hermes profiles. Their source configurations are in `config/hermes-cloud/`; `node scripts/hermes-cloud-profiles.mjs <architect|foreman|peon>` creates a profile, copies the existing role SOUL and applicable role skills, and validates the loaded model, provider, fallback list, and toolsets. Offline prompt inspection confirms that role skills loaded and no direct tools are exposed; an empty tool inventory fails qualification. An existing cloud profile requires an explicit `--replace`. Each CLI inspection has a 30-second deadline. This command never copies authentication files. The installed Hermes `openai-codex` credential is borrowed through its native provider. The original `architect`, local `foreman`, and governed `peon` profiles remain intact; the local Qwen routes are separate choices, not automatic fallbacks. Mira and Designer are unaffected.

The three cloud profiles expose only the skills toolset. Terminal, file, browser, code execution, connections, delegation, and memory tools are disabled. They have no fallback providers or auxiliary title inference. These profiles can perform bounded planning or review conversation, but no trusted orchestration or production cloud Peon coding route is connected yet. They do not grant GitHub, worktree, merge, approval, or credential authority. Use the trusted host and existing issue policies for any future assignment. A listed Hermes gateway or configured profile does not prove an agent is active.

The provisioner uses the absolute profile directory reported by the same Hermes CLI that creates and inspects the profile. It shares the local provisioner's identity-file guards: linked directories and symbolic-link destinations are rejected, and config/SOUL replacement stages a fresh file before renaming it. Existing hard links therefore cannot redirect those replacements into another role's file. These checks assume a trusted local host; concurrent filesystem tampering is outside the provisioner's isolation boundary. Run `node --test scripts/hermes-cloud-profiles.spec.mjs tools/policy/engineering-org/provision.spec.mjs` for offline qualification without invoking Hermes.

## Short-session records

The intended session boundaries are planning, technical dispatch, one implementation attempt, one fresh Foreman review per Peon result, Foreman reconciliation, and Architect approval. Conversation state is temporary. Templates are behavioral identity; approved profile memory is non-authoritative. GitHub is authoritative for issues, dependencies, PRs, and integration. Host-generated immutable attempt evidence and revision-bound review/reconciliation records are authoritative for execution facts. Persist compact task packets and records; never rely on a long-running conversation or replay full transcripts to recover work.

Fresh issue/claim/worktree/budget facts must be checked at every host operation. Idempotency keys, session IDs, attempt leases, exact revision checks, and safe-cleanup confirmation prevent duplicate or stale actions. Provider quota, timeout, authentication, context, and network failures remain distinct; none implies approval. If Architect is unavailable, previously authorized work may continue. Integration still waits for Architect or CEO approval.

The [offline planning contract](engineering-planning.md) validates issue quality, duplicate-search coverage, anticipated scope risk, capability history and dependency order against a revision-bound trusted snapshot. It can save exclusive, integrity-checked recommendation records. It does not authenticate a live caller, fetch host facts, mutate GitHub or dispatch workers; those boundaries remain part of the trusted orchestration work.

## Host session boundaries

The orchestration modules under `tools/policy/engineering-org/host-*.mjs` separate repository admission, process sessions, evidence storage, candidate snapshots and lifecycle coordination. The current executable recipes are inert qualification programs. Registering a live recipe is rejected. Passing these tests does not qualify Hermes, a model provider, a coding sandbox or an integration route.

The host constructs repository admission from its trusted checkout and a scope receipt outside the worker worktree, with a separately retained digest. Admission reads current issue and native dependency state, the active claim, the registered clean worktree and current `develop` revision through the existing policy helpers. It checks the exact issue and policy bindings, bounded acceptance criteria, capability evidence and conservative one-attempt limits. Two matching reads detect authority changes during inspection. Constructor dependencies and scope receipts belong to the host; model packets cannot select readers, authorize capabilities or fabricate an admission handle.

The host also registers purpose-specific recipes against an expected script hash. The child process handle and its private IPC channel establish the session role; a role name in model output does not. Session packets are detached before asynchronous work, and receipts are immutable. The runner bounds packet size, output and time, forwards only the small platform environment required by the inert child, and records termination separately from success. These trusted inert programs are not a sandbox for arbitrary code. A future live adapter must prove its own isolation and cleanup before activation.

Candidate qualification uses a disposable Git commit containing the proposed changed files, together with the original source revision and a content digest. This is a change snapshot, not a complete build checkout or eventual PR head. Verification compares the recorded file contents with both that commit and the files on disk. The current envelope supports bounded text additions and modifications; unsupported execution or file operations must not be inferred from the more general review-report schema. A later real PR requires evidence bound to its actual head.

Evidence records use bounded, exclusive writes and file synchronization. Their integrity depends on host-controlled storage and retained digest bindings; a self-consistent JSON hash is not authentication. Tests include separate processes racing for the same reservation, stale release attempts, forged session handles, credential exclusion and changed candidate bytes. Filesystem synchronization does not establish universal power-loss guarantees. Torn or uncertain records must stop recovery rather than permit an automatic repeat.

`createEngineeringHost` accepts the host's admission handle, registered recipes, journal root and shared pool root. Its operations are `prepare`, `execute`, `review`, `reconcile` and `recover`; `run` follows the normal sequence. The request to `prepare` contains only the issue number, supervisor claim session ID and idempotency key. Repeated requests must match their stored grant and recipe hashes. Changing a key or recipe does not create another attempt for the same issue, session and revision. The journal must remain stable across restarts; creating a fresh journal is not a recovery procedure.

When another session holds the shared slot, preparation retains the admitted grant and reports `queued`. Retrying the same request and key performs fresh admission before dispatch. `run` also returns the queued outcome without starting implementation. This permits independent tasks to wait while actual sessions remain serialized; it does not create a second GitHub issue-status system. Uncertain storage failures are errors, not queue signals.

Preparation invokes a bounded Foreman dispatch session. Execution reuses `superviseWorker` with one Peon attempt and a separate verifier session. Each completed attempt record receives a fresh Foreman review session, including a blocked failure report when no verified candidate exists. Reconciliation consumes compact persisted review summaries, without replaying implementation conversations. Re-reading an existing result or review does not launch a replacement session. A passed reconciliation means ready for integration review, not permission to merge.

The host saves a phase reservation before launching its child and records the launch and result separately. Implementation and verification share one operation lease, acquired before consuming the attempt. A busy slot therefore leaves an unstarted attempt queued, and another task cannot take the slot between implementation and verification. Their phase records remain separate; releasing the operation requires confirmed termination and a durable cleanup record. All hosts using the same pool root serialize their sessions. This only covers participating hosts; it does not lock unrelated model servers, another pool root or the existing live pilot runner. Before any live activation, the machine's actual Foreman, Peon, meter and client lifecycle must share one enforced resource pool, including across clones.

Recovery inspects the shared slot and persisted launch/result records. A stopped child with a retained result can permit release only after the original host and child are absent and their records agree. Missing launch evidence, an uncertain result, an active process or inconsistent records leaves the slot quarantined. Recovery never re-executes a consumed phase, and a request cannot assert that cleanup succeeded. Keep the original records and resolve uncertainty through trusted inspection; do not delete reservations or change journal roots to force a retry. New work requires fresh admission and authorization.

Run the complete inert qualification with:

```powershell
node tools/policy/engineering-org/host-run.mjs qualify
```

It creates a temporary repository, claim and host evidence directory, runs the fixed inert lifecycle and prints the retained evidence path and outcome. It does not contact a model provider or change repository issues. The separate `admit` command reads a real assignment using `--repository`, `--scope`, `--digest`, `--issue` and `--session`; the first two paths must be absolute and the digest must come from trusted host configuration. It reports admission facts without launching a worker. Neither command supports live execution.

## Offline review qualification

Issue [#97](https://github.com/DanielssonThomas/Stellar/issues/97) adds a deterministic review contract qualification suite. Run it with `node --test tools/policy/engineering-org/review-report.spec.mjs tools/policy/engineering-org/review-file-changes.spec.mjs`. It uses repository-owned pure numeric-level and module-export fixtures with authored review responses, without network, credentials, model calls or worker execution. Local probes execute correct behavior, an upper-bound defect, a lower-bound regression and a missing non-number input criterion. Another fixture deliberately withholds the simulated trusted test record despite a worker's passing-test claim; its expected decision is `blocked`. The harness still exercises that fixture's code to distinguish correctness from available review evidence. File lifecycle probes import only fixed fixture source in memory and verify deleted, emptied and newly empty modules, including an intentional obsolete-export deletion that passes.

`validateReviewReport`, re-exported from `authority.mjs`, now requires report schema version 2. The only previous caller was an offline test; version 1 reports are rejected rather than silently upgraded. Reports bind to the expected issue, full baseline and candidate Git SHAs, canonical author and Foreman reviewer. Separate host context supplies all criterion IDs, complete changed-file evidence, and verification IDs, commands and actual statuses. Each file has `status` (`added`, `modified` or `deleted`), `baseLineCount` and `headLineCount`; zero lines are valid. Deleted files remain in the manifest with zero candidate lines; represent a rename as a deletion at the old path and addition at the new path. An empty manifest still means missing change evidence. Findings use `side: base` or `side: head` with a valid line on that revision, or `side: file` without a line for file-level concerns and verification. Every criterion and check must appear exactly once. Findings must identify a criterion, explain impact and a correction, and reference the affected check for verification failures. Contradictory decisions, omitted evidence, unsupported passing-test claims and self-review are rejected.

The suite verifies the supplied review contract and the expected outcomes of these bounded fixtures. It does not measure a model's ability to discover defects, establish reviewer identity, authenticate host records, prove the semantic truth of arbitrary findings, or grant execution or merge authority. A live host must obtain fresh evidence independently of model output and resolve identity aliases before supplying context. Trusted acquisition, session provenance, replay protection and recovery belong to #99; live qualification belongs to #101. Review reports never replace independent assessment or management authorization.

## Current implementation boundary

The [controlled integration guide](worker-integration-policy.md#offline-architect-decisions) describes the offline exact-PR review and Architect decision host. It keeps source snapshot review, actual PR-head review, management judgment and merge authorization separate. Its inert decisions cannot activate integration, and the existing manual runner requires complete fresh protection evidence. The shared dependency-identity correction in [#190](https://github.com/DanielssonThomas/Stellar/issues/190) is an additional live-qualification prerequisite.

Epic [#95](https://github.com/DanielssonThomas/Stellar/issues/95) coordinates this work. Issue [#96](https://github.com/DanielssonThomas/Stellar/issues/96) covers identity templates, provisioning, and offline authorization. Existing `worker:peon` compatibility and Mira escalation paths remain in place. This slice does not activate Architect inference, Foreman inference, live Peon runs, multi-instance inference concurrency, or fallback merging. A live pilot requires a separate CEO decision after offline qualification and governance review.
