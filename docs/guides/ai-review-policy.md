# AI review priority policy

Issue delivery priority and AI review tier answer different questions. Priority sets scheduling urgency. Review tier sets the minimum assurance and model budget for code review. Every new actionable issue from #103 onward has exactly one `review:*` label. Issues through #102 are historical and may omit it; their requested tier defaults to `standard` for PR review. A valid explicit tier on a historical issue takes precedence over that default.

Architect chooses an initial tier while planning an engineering-organization issue. Foreman can recommend escalation in its review report. Neither role controls the minimum for actual changed files. The trusted host reads the current issue labels and the complete GitHub PR files list, including both names for renames, from GitHub. It checks the PR `changed_files` count and evaluates `tools/policy/ai-review.mjs` from the authorized target branch. Unreadable, incomplete, or malformed file evidence denies review. The effective tier is the higher of the issue tier and file classification.

The file classifier assigns `critical` to protected governance paths, workflows, policy and generator scripts, credentials, authentication, authorization, isolation, metering, billing, budgets, security names, and key material. Other code gets `standard`; ordinary documentation gets `light`. Unknown paths are at least `standard`. Renames classify both the old and new names. The trusted host must re-fetch the head SHA, changed-file count, and issue tier before creating a final check; a head or tier change needs a new review key.

## Offline dispatch contract

`tools/policy/ai-review-config.json` defines model IDs, maximum input and output tokens, provider price ceilings, per-request and per-session spending caps, request and retry ceilings, and a **$5 monthly cap** for the whole dedicated Stellar API project. Dispatch remains disabled. These model IDs and prices are policy ceilings, not evidence of current provider availability or pricing. A trusted host must independently verify the model, current price, output-limit support, and provider-side project cap before enabling any route. Billing auto-recharge must remain off. No API key or paid request is provisioned by this policy.

`tools/policy/ai-spend-ledger.mjs` provides a shared append-only, fsynced spending journal for future provider callers, including Architect, Foreman, Peon, and PR review. Every caller must use the **same absolute ledger path on a filesystem with exclusive-create locking semantics**. An operator must create the journal and durably sync its file and containing directory before any paid route is enabled. Transactions never create a missing journal: a missing path fails closed, including before the first request. The operator must also verify locking and storage durability across every host and agent. The journal reserves the worst-case request charge before inference. Session request and dollar ceilings include the complete journal history for that session ID, even across UTC month boundaries; only the project monthly cap resets at a month boundary. A conflicting or abandoned lock, malformed or incomplete journal, uncertain charge, missing usage, unknown model, unavailable provider, unverified price, unsupported token ceiling, quota failure, or exhausted limit denies a new call. Uncertain charges retain the entire reservation. There is no automatic paid retry. The journal does not contain prompts, secrets, or raw provider output. `ai-spend-report.mjs YYYY-MM` reads `STELLAR_AI_SPEND_LEDGER` and prints only monthly committed and reserved USD totals and route counts. A hard provider-side project cap at or below the CEO ceiling is required before activation. The existing `reserveReview` in `ai-review.mjs` remains an offline planning adapter; a live dispatcher must reserve through the shared ledger and never treat a per-job array as spending authority.

`reserveReview` returns a reservation keyed by repository, PR number, head SHA, and effective tier. Its trusted store adapter must serialize `transact` across all PRs and durably commit the returned ledger before returning the plan; an in-memory or per-job adapter is insufficient for live dispatch. A provider call may start only after a successful `reserve` result. The transaction reserves the worst-case charge against the monthly cap, counting pending reservations and actual completed charges across all PRs. If another run owns the key, reuse its state without a second call. `finishReview` records trusted usage; `failReview` records terminal failure. An interrupted call stays pending and blocks the required check; automatic retries on the same key are forbidden. Manual recovery needs explicit maintainer action and audit evidence. A new head or higher effective tier gets a new key. This design prevents duplicate inference from repeated webhooks and unchanged code.

The host passes only bounded text from the GitHub diff to the model. It must reject or truncate input before the route's input token limit, set the output token limit explicitly, and abort if the provider cannot enforce it. It must obtain usage and cost from trusted provider billing, then call `completeReview`; model prose cannot supply accounting data. The public report contains only model route, tier, head, integer input/output token counts, rounded USD charge, and sanitized findings. It excludes prompts, raw provider responses, credentials, and billing identifiers. Missing usage, excess usage, an unavailable provider, exhausted budget, or a missing completed record fails the review gate. The disabled configuration currently causes `provider-disabled` and makes a required live review fail closed.

A future credential-bearing review job must check out only the trusted base policy with persisted checkout credentials disabled. It may fetch PR metadata and diff text through read-only GitHub APIs. It must never check out or execute PR code, install PR dependencies, run PR scripts, or send credentials into a worker session. Treat code and review prose as untrusted input. `reviewGate` checks completion for the exact head and effective tier; it does not treat the model's recommendation as merge authorization.

## GitHub enforcement proposal

Active ruleset 25456574 covers `main`, `develop`, and `release/**`. It requires a PR and the `verify` check, blocks deletion and force push, requires zero approving reviews, and has no bypass actors. After a separately approved provider, durable ledger, trusted review job, and check publisher are qualified, add a stable `ai-review` required status check from that trusted GitHub App to the same ruleset, retaining `verify` and strict required checks. Publish success only for a completed review at the current head and effective tier; missing review or quota failure remains pending or failed. Do not use `pull_request_target` to execute PR code. The AI review is an independent recommendation and check. GitHub rules, human or Architect approvals when applicable, and the trusted integration gate still decide merge authority. Do not mutate the ruleset or grant bypass while dispatch is disabled.
