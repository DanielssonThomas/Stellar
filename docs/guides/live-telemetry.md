# Stellar Live telemetry foundation

Issue #164 provides a local, read-only feed of Hermes turn activity. It does not launch agents or change their runtime. PR #163 owns the Operations and Character Studio UI; the Live view is a separate integration step after that PR is resolved.

## Run locally

Use Node 22. Set `STELLAR_HERMES_ROOT` to the actual Hermes home if it is not `D:\Hermes`, then run `node tools/live/server.mjs` from this checkout. The server binds to `127.0.0.1:4212`. `GET /api/live` returns the latest allowlisted snapshot. `GET /api/live/events` streams snapshots through Server-Sent Events with a heartbeat every two seconds; clients can fall back to polling `/api/live`. Only the local Angular origins on port 4200 receive CORS permission. No request accepts a file path, command, session selector, or arbitrary query.

## Live dashboard behavior

Start `node tools/live/server.mjs` alongside the dashboard adapter and Angular app described in [operations-dashboard.md](operations-dashboard.md). Live is the default tab. It groups nine configured Hermes identities into Code Bay, Review Deck, and Creative Studio, and recent Codex turns into Codex Corner. Work motion and the running count require a fresh observed running lease. A disconnected or stale source demotes visible execution to unknown and clears current activity; recorded timeline events remain labeled as history. Project filters and agent selection are local display controls. EventSource reconnects automatically, and polling checks freshness every five seconds. Reduced-motion users see static workstations.

The inspector shows only source-supported model, provider, usage, activity and tool category. Task text remains unavailable until a verified structured task binding exists. The browser receives no prompts, commands, credentials, raw paths or privileged controls.

The collector opens nine named Hermes profile databases read-only, plus two fixed Codex history databases read-only. It selects lease, session lifecycle, model, provider, token counts, and tool-name columns. It never selects prompts, model content, private reasoning, tool arguments/results, command text, filesystem paths, or credentials. Browser session IDs and event IDs are short one-way hashes. Tool names map to fixed broad labels; unknown names become “Tool invocation.” Overlapping tool queries are deduplicated by source session and message ID before ordering and applying the 40-event per-agent limit. The SSE server permits at most 16 simultaneous clients and drops any client whose queued output reaches its 128 KiB bound or remains backpressured for two seconds or another packet. EventSource may reconnect or clients may poll. A collector failure changes agents to `disconnected` and clears visible activity.

The feed currently uses `running`, `completed`, `failed`, `disconnected`, and `unknown`. It does not claim `idle`, `queued`, or `blocked` without a verified runtime source. The latest recorded tool event is displayed as current activity only if it occurred after the live lease was acquired. The collector deliberately omits freeform message text and task titles pending a safe, structured source.

## Codex desktop sessions

Issue #170 adds recent standalone Codex turns to Codex Corner. The collector opens the fixed local `.codex/state_5.sqlite` and `thread_history_1.sqlite` databases read-only. It associates only checkout folder names matching Stellar or Stellar-Design. It selects thread IDs, turn lifecycle, timestamps, and item types; it never selects item JSON, titles, message bodies, tool arguments, commands, or full paths for the browser. IDs are hashed, and item types become fixed generic activity labels.

An `inProgress` row appears running only when its latest recorded item is no more than five minutes old. Older unfinished rows are unknown or omitted after 30 minutes. Recent terminal statuses show completed or failed without animation. A missing or changed database produces a disconnected Codex source card. The local Codex database schema is internal runtime storage, so this is a best-effort read-only integration rather than a supported external telemetry contract. The source label in the inspector distinguishes it from Hermes leases.

## Task-summary source investigation

Hermes session rows have `last_activity_description` and `last_activity_provenance`, but the inspected profile databases contain mostly empty descriptions with `unknown` provenance. The field is freeform and is not a safe task label. GitHub owner/status labels and issue worktree claims record assignment, not live execution; they also lack a verified join to a Hermes turn lease. The current Stellar-Design phase record has `current_session_id: null`, so its character assignment cannot be attached to a live Designer turn. Supervisor handoffs contain structured Peon issue identity, but the restricted worker's process and session evidence do not yet reach this feed. A future task summary requires a trusted, local, allowlisted binding of profile, session, issue or character ID, bounded activity category, timestamp, and lifecycle outcome. That binding must be reviewed independently of execution authority before the UI displays it as current work.
