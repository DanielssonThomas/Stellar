# Guardian registry and original connection custody

Status: CRITICAL TECHNICAL DEVELOPMENT DESIGN REVIEW ACCEPTED. No positive authority, OS call, listener, prompt, launcher, registry or activation is implemented by this document. Cooperative TCB remains proposed and NOT user-accepted. Immutable v3/channel/journal contracts remain unchanged. This additive design follows producer61084a and consumer e216f69. The immutable consumer import includes runtime source; the new consent Cargo dependencies and client module composition are TEST-ONLY. No imported application or native runtime is launched.

Independent critical review resolved the affirmative-action, all-three-pairs authentication and scope-wording findings before this record was sealed. Acceptance permits only later isolated registry/denial-state development with production factories unavailable; private codec still needs exact wire review. It grants no positive OS/launch/host-ticket implementation or operational/TCB acceptance.

## Concrete missing seam

The actual host object is `gateway.session_controls.AuthorityConnection`: it retains `authority`, `transport`, actor and subscriptions. Its close path detaches subscriptions and removes transport state. Actor equality and `_native_legacy_transports` are intentionally insufficient: existing source also admits other owner contexts. The current Desktop bridge discovers a gateway and constructs IvyConnection; the native Broker launches bridge Python from mutable runtime selection. Neither is the owned four-process registry below. No live process is adopted, reclassified or silently replaced.

The currently public `host_connection_v3.attach` stays unconditionally unavailable. Its private `_ConnectionPlan` remains DATA only. It will not be promoted by enabling a flag or passing a callback returning true. A future factory needs three genuine private owners: verified launch/code custody, two-sided OS channel custody, and the actual original AuthorityConnection object. Guardian callback association is an additional one-use input to consume, not an attach-time boolean.

## Threat claim and retained release authority

Proposed protection covers model/plugin/renderer text, unregistered local peers, stale or replayed channel frames, actor/PID/path/nonce impersonation, wrong process/session/profile, endpoint squatting, process exit/replacement and scope/policy/cancellation races. Names, hashes, handles serialized as numbers and successful OS API return codes alone confer no application authority.

The cooperative same-user boundary does NOT resist an attacker able to modify or inject into admitted guardian/host/bridge/Desktop code or memory, duplicate their private handles, tamper with the approved loader/OS, or automate their trusted UI/verification flow. It supplies no physical-human-presence or transaction-signing guarantee. Same-user pipe clients without those capabilities must still fail exact retained-peer checks. Logon ACLs are not process authentication. No admin, service account, secret credential, new protected-process boundary or general approval-policy change is proposed.

Externally accepted release-policy custody is ABSENT. The fixed approved-root reader must later obtain authenticated policy through a separately reviewed coordinator/owner mechanism; no CLI path, model text, current-user writable manifest, caller hash or self-enrollment can establish that root. Existing CodeManifest/LaunchManifest only validate data and executionEnabled remains false. Strict hardlink/alias and complete loaded Python/DLL/native-module closure remain unqualified, including serviced Windows components. Refuse unsupported closure rather than inventing an exception or expanding this threat claim. Positive launch cannot exist until those exact prerequisites are qualified and separately accepted.

## Two-sided process/channel attachment

Final server/client roles preserve v3: guardian creates native-client server and retained Desktop opens it; host creates private authority server and retained guardian opens it; host creates canonical server and retained bridge opens it. Inherited bootstrap endpoints are rendezvous only, never fresh peer identity. Desktop/bridge stdio is a separately owned inherited pair, never a discovered process.

Future launch uses explicit application paths, fixed args, a minimal fixed environment and explicit inherited handle list; no shell/PATH search or arbitrary argv. Guardian obtains a real self-process handle before child launch, not a pseudo handle in inheritance. It creates host suspended with only exact bootstrap/guardian-reference handles, constrains owned-process cleanup and validates loaded closure before admission. Child policy, environment and module/DLL/OS alias qualification remain blockers, not assumptions that suspended launch solves loader races.

Host starts its private authority listener only under an admitted launch. Guardian connects; BOTH sides query actual pipe peer PID from the connected pipe, open a process reference with only reviewed query/synchronization rights, compare the underlying process object to the retained counterpart, and check liveness before/after registration. `CompareObjectHandles` is the proposed exact object comparison; PID/creation-time string equality alone is rejected. Failed queries/comparison/termination deny. Retaining a handle is not claimed to make PID reuse impossible.

This requirement covers ALL three final pipe pairs:

| Pair                      | Server validates client against                                              | Client validates server against                      |
| ------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| guardian-native / Desktop | Guardian's retained Desktop process reference                                | Guardian process reference inherited by this Desktop |
| host-authority / guardian | Guardian process reference inherited by this host                            | Guardian's retained host process reference           |
| host-canonical / bridge   | Bridge process reference duplicated into this host by authenticated guardian | Host process reference inherited by this bridge      |

References supplied to children are real reduced-right process handles (`SYNCHRONIZE` and reviewed query-limited access), never write/injection/duplication authority. Only the precise creation handle list is briefly inheritable; the child immediately clears inheritance on its references. Later DuplicateHandle transfers set bInheritHandle=false. The guardian alone retains separately reviewed creation/termination/duplication rights needed to manage its own children. An imported numeric handle is never accepted on ordinary RPC. Parent/child cleanup and duplicate-ACK uncertainty must close exact retained objects, not reopen by PID.

The current v2 launch recipe's fixed inheritedHandles policy cannot itself encode these role-specific reference lists. This design is NOT a newly accepted interpretation of that immutable field. A future exact versioned launch recipe/loader amendment and critical review are prerequisites before a positive executor; current v2 validation and executionEnabled=false stay unchanged.

Guardian later creates bridge/Desktop with exact owned bootstrap/stdin/stdout handles. For host peer expectations created after host launch, guardian duplicates only retained bridge/Desktop process references INTO that owned host process. Transfer occurs solely on the already authenticated guardian-host port; target-handle numbers are local locators, not proofs. Host validates one-use slot/launch generation/type/rights, compares the actual newly accepted canonical bridge peer against the retained process object, and closes/refuses unexpected/duplicate handles. No arbitrary caller PID/path/process handle is registered. A dropped/ambiguous duplicate/ACK consumes its slot and denies the graph; never resend a duplicate-handle operation to infer whether it happened. OS handle ownership/cleanup must be separately implemented/reviewed before any such operation.

Pipe instances use first-instance collision refusal, local-only clients and exact current-logon DACL. Endpoint nonces only disambiguate a launch; possession is not authentication. Subsequent replacement/reconnect creates no lease, even if labels/nonce match. A new graph cannot clear the durable profile latch. No production listener is created by test integration or future pure-state fixtures.

## Original canonical connection registry

Host is the sole registry writer on its authority loop. On actual owned canonical accept, BEFORE ordinary dispatch, it creates the real AuthorityConnection through its transport gate and stores a strong reference with the exact transport object, authority object/epoch, process/channel reference and fresh generation. No row, actor map, subscriptions snapshot or serialized connectionBinding reconstructs this reference. Profile-scoped Ivy only; no sibling/shared-host fallback.

Guardian-host channel is associated privately with that single owned bridge slot and Desktop native channel in the same launch graph. Association is consumed once. No ordinary request chooses a lease by attachmentId, launchId, connectionBinding or actor. A second connection with equal fields is another object and fails. Original `session_id` is host-resolved on reserve; host captures physical target, route, registered producer/incarnation, owner/options/policy and original session. Compression/reset/session selection or authority re-serving denies, never follows a newer tip automatically.

Future private factory signature is conceptually `attach(OwnedHostPeer, RegisteredCanonicalConnection, ApprovedPolicyLease) -> NativeLease`; all parameters are private owned capabilities, not dictionaries or caller-implemented traits. It captures the journal Context/Prepared data only AFTER those owners validate. Before every positive operation and inside the actual write callback, verify exact object identity, retained live generation, authority epoch/admission-open, exact subscription/transport registration, original origin/policy/consent/deadline and sticky deny. Data-plan equality checks remain defense in depth, not this gate.

Canonical connection close, channel EOF, peer exit, pending window loss, policy change, reset/compression or explicit opt-out first marks a shared deny generation synchronously under a short lock, then schedules tracked canonical cancellation. The worker's gate reads that same deny generation inside its transaction; no separate unsynchronized bool. No owner-loop lock spans SQLite wait/OS verification/I/O. Physical cancellation may lag canonical revocation and must retain obligations. Registry entries are tombstoned/spent in memory; restart leaves DB exclusion intact. No rehydration/inspect-to-resume factory exists.

## Native window and one-use OS callback

#299's future UI creates the actual guardian-hosted window, owns native resource lifecycle/thread affinity and exports an owner-bound borrowed parent. Guardian alone requests the OS verifier and owns its async operation/callback. Caller HWND, renderer action, ClosedObservation or a decoded `Verified` string cannot construct verification authority.

Exact prospective #299 interface delta, relayed through Ivy only: retain `OwnedScopeWindow`, `WindowStamp`, `NativeParent<'owner>` and one-use close observation; provide a Windows parent borrow for producer OS interop with lifetime tied to that actual owner, plus actual Destroyed/Cancel events. No public constructor from integer HWND and no public arbitrary verifier/backend. An OS-call-only raw view, if required by FFI, is a borrowed DATA locator usable only in the reviewed guardian wrapper; it is not a trust token. Consumer owns its implementation. Current `present_native`/`borrow_native_parent` continue returning Unavailable.

Guardian registry stores actual window owner/stamp/generation, creating UI thread and a one-use callback slot linked to the existing private Attachment and prepared/policy/generation digest. Immediately before OS request it validates owner-thread/resource/liveness, then journals begin BEFORE entering the OS API. Only the actual returned IAsyncOperation associated with that slot can settle it. First settlement consumes it atomically even for error/cancel; duplicate/late/foreign-operation callbacks cannot create Verification or GrantIntent. A reused HWND fails the retained owner/stamp/generation association. Thread marshaling captures only the owned slot/operation; no renderer or arbitrary result enum fills it.

BEFORE journal begin or any OS request, require a fresh one-use affirmative request from this exact original owned window/generation displaying the complete immutable original Prepared scope, render/speech effects, expiry and admission budget. Guardian compares that display association to its retained Prepared/policy digest and consumes the affirmative slot once. Cancel, changed scope, a different window, a replayed/late affirmative or detached origin refuses. OS Verified alone never satisfies this explicit consent gate. Tests must cover affirmative replay/foreign generation, changed displayed options and Verified-without-affirmative, with zero OS/request/begin effects on refusal.

Call `IUserConsentVerifierInterop::RequestVerificationForWindowAsync` only with the actual active application parent and immutable literal scope message. S_OK means operation creation, not verification. Require that exact async result to be Verified; all unavailable/error/nonverified outcomes deny with no fallback dialog/PIN emulation/enrollment. This is Windows user verification under proposed trusted code, not cryptographic signing of Prepared. UI automation/code-tampering limits above remain explicit.

Cancellation reader remains independent of the OS wait and reserves capacity under v3. Local deny/slot-consumption happens first. Best-effort cancellation of that exact async operation is separate from observing its termination; unresolved callback/window resources remain owned/quarantined until observed settlement. A timeout does not certify closure and does not permit a new attempt. New private native success constructors may only be implemented after this actual callback/owner wrapper receives separate critical unsafe/custody review.

## Private host ticket, retirement and canonical bind order

Use a SEPARATE typed private host-method codec over v3 bounded framing; do not feed host verbs into the consumer's existing three-method codec or add them to canonical/model RPC. Keep the existing four private methods and closed params exactly as v3 design: reserveConsent(session_id), beginConsent(challengeId,preparedDigest), consumeConsent(challengeId,preparedDigest,intentId), cancelConsent(challengeId). Native client frames and canonical gateway limits remain unchanged. All IDs/digests remain DATA. Source authority is the retained private peer/lease, never params.

1. Private reserve captures original connection/scope and creates the durable profile latch before Prepared ACK. Client/host keep bounded consecutive correlation and no retry. begin reserves confirming before any OS call.
2. Guardian consumes only its genuine operation callback and broker GrantIntent, reserves local host effect once, generates one intentId and sends consume on that exact private host port. There is no serialized OS-proof field.
3. Host validates original lease/digest/sequence, durable confirming and sticky deny; reserves issuing BEFORE creating a raw random ticket. Future ticket constructor is private to this handler, not existing actor-only Host.approve. It binds the exact connection object/generation, scope/policy and fixed deadlines. Record only ticket hash; reserve release in canonical transaction before returning ticket once. Unknown creation/commit/release/ACK seals, never repeats or reconstructs. The existing DATA plan supplies the transaction mechanics, not authorization.
4. Only a matching authenticated consume reply AFTER known ticket record/release commit creates private HostConsumeSuccess for WindowFlow. This evidences consume/issuance, NOT a completed canonical bind. The guardian must have genuine callback custody too. It then authorizes its own deliberate UI close, observes matching owned destruction and consumes ClosedObservation for the original stamp. Pending user Cancel/premature destruction is processed as denial; merely receiving ClosedObservation is never consent.
5. Only after that deliberate close observation and a fresh lease/deny/deadline check may guardian enqueue complete's ticket result to the original Desktop native channel once. Already queued bytes may arrive after a later cancellation; they cannot bypass host bind denial. Missing close observation/lost ACK/cancel retains uncertainty and never reopens/reissues.
6. #299 native adapter treats Event::Ticket as transient DATA and transfers it once through the SAME retained canonical Broker/bridge connection. Future consumer factory takes a guardian-owned inherited bridge client instead of spawning/discovering another bridge. This requires a distinct owner-bound stdio/process-reference type; it must not fabricate Rust Child or imply Desktop spawned/owns the guardian's bridge. Guardian retains child cleanup ownership. No WebView-supplied ticket and no new bridge fallback. This consumer source change is #299-exclusive and currently absent.
7. Host's bind handler matches exact AuthorityConnection object/lease, ticket hash/state/original scope/policy/clock/deny inside the existing canonical write. Existing plan's one-shot Ledger facade chooses revision, inserts binding+owner and consumes journal atomically. Known binding result is a binding DTO/receipt, never retroactive callback evidence. Intentional UI retirement does not require HWND to remain live through bind; all connection/process/policy/consent gates persist.

Prepare/consume/bind have one positive effect in flight. Cancellation is independent and ordered by canonical writer: cancel-first refuses release/bind; bind-first atomically revokes and retains exact queued/started/effect obligations. The private cancel result never claims physical speech stop. Lost bind ACK remains uncertain; no not-found/query/tombstone/reconnect authorizes resend. Retain all original journals and fences; no new schema/migration or retirement/reset endpoint is proposed.

## Primary evidence and limits

- Microsoft [window-bound verifier](https://learn.microsoft.com/en-us/windows/win32/api/userconsentverifierinterop/nf-userconsentverifierinterop-iuserconsentverifierinterop-requestverificationforwindowasync) specifies an active application HWND and asynchronous verification result, minimum Windows build22000. It does not promise Prepared transaction signing.
- Microsoft [pipe client PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid) and [server PID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid) expose OS peer observations. Proposed process-object comparison additionally uses [CompareObjectHandles](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-compareobjecthandles); these APIs do not attest loaded application code.
- Microsoft [explicit inherited handle list](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [process creation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) and [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle) define object custody mechanics and target-process handle locality. This proposed protocol is an inference/design from those mechanics, not an OS-provided consent broker.
