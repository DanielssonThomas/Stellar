# Consent journal v3: exact isolated development proposal

Status: **PROPOSAL FOR CRITICAL SCHEMA REVIEW BEFORE IMPLEMENTATION**. Parent source a6864df. Existing six immutable contract/design artifacts stay byte-identical. Only new producer-owned candidate modules and an inert connection-local ledger revocation extraction are proposed. No production factory, RPC, positive proof, native/OS/launch integration, managed migration or original journal access is authorized. TCB remains proposed, not accepted.

## Scope and conservative fence

Implement pure Python transaction-domain functions in new `config/hermes-compat/native-consent/journal_v3/`, not automatically imported/installed by the existing host package. No function opens a DB, starts/commits a transaction, invokes an external effect, issues a ticket or configures a runtime. A one-shot wrapper delegates to the existing canonical writer without owning its transaction. The host alone owns the eventual canonical connection and writer; tests use new disposable DBs only.

This initial candidate deliberately keeps a **permanent retained profile latch**: one native-consent attempt for Ivy per canonical DB, including cancelled history. `UNIQUE(profile_id)` plus no deletion prevents a fresh launch/epoch/attachment bypass. This is stricter than the unresolved-only minimum in immutable v3, not an authority expansion. There is no retirement/reauthorization protocol or timeout release in this slice. A future safe release/migration must be separately reviewed. Thus <=16 pending/<=64 retained upper bounds are satisfied conservatively; repeated opt-in after known cancellation is unavailable, rather than inferred safe from time/absence. No automatic recovery operation is introduced.

The journal is NOT an execution queue, ordinary plugin API, trusted native attachment or consent proof. Context/Prepared inputs are host-domain data, never authority merely because they match a DB row. A future authenticated host adapter must revalidate the actual original connection object/lifetime/profile/physical target/route/producer/policy in the canonical writer before calling positive transitions. Those adapters and operational constructor remain absent.

## Exact DDL

SQLite >=3.37 STRICT tables are required; refusal otherwise. SQL statements are individually executed inside the existing canonical `BEGIN IMMEDIATE`, never executescript, PRAGMA user_version changes, implicit commit, nested BEGIN or another database. All journal verification/DML/DDL explicitly targets main. `hex64` below expands literally as `length(CAST(x AS BLOB))=64 AND length(x)=64 AND instr(x,char(0))=0 AND x NOT GLOB '*[^0-9a-f]*'`; hex32 uses32 in both lengths. Byte length and NUL refusal prevent SQLite text-length/GLOB truncation aliases. Nullable identifiers additionally require `x IS NULL OR (...)`. All TEXT bounds are UTF-8 byte lengths using length(CAST(x AS BLOB)). This notation defines exact repeated CHECK expansion, not a permissive SQL type.

```sql
CREATE TABLE main.stellar_nc_meta_v3 (
 singleton INTEGER PRIMARY KEY CHECK(singleton=1),
 schema_version INTEGER NOT NULL CHECK(schema_version=3),
 schema_digest TEXT NOT NULL CHECK(hex64(schema_digest)),
 retained_count INTEGER NOT NULL CHECK(retained_count BETWEEN 0 AND 64)
) STRICT;

CREATE TABLE main.stellar_nc_attempt_v3 (
 challenge_id TEXT PRIMARY KEY NOT NULL CHECK(hex64(challenge_id)),
 profile_id TEXT NOT NULL UNIQUE CHECK(profile_id='ivy'),
 attachment_id TEXT NOT NULL UNIQUE CHECK(hex64(attachment_id)),
 context_json TEXT NOT NULL CHECK(bytes(context_json) BETWEEN 1 AND 8192),
 context_digest TEXT NOT NULL CHECK(hex64(context_digest)),
 prepared_json TEXT NOT NULL CHECK(bytes(prepared_json) BETWEEN 1 AND 16384),
 prepared_digest TEXT NOT NULL CHECK(hex64(prepared_digest)),
 created_ms INTEGER NOT NULL CHECK(created_ms BETWEEN 0 AND 9007199254740991),
 phase TEXT NOT NULL CHECK(phase IN ('pending','confirming','issuing','issued','bound','cancelled')),
 deny_requested INTEGER NOT NULL CHECK(deny_requested IN (0,1)),
 intent_id TEXT UNIQUE CHECK(intent_id IS NULL OR hex64(intent_id)),
 ticket_hash TEXT UNIQUE CHECK(ticket_hash IS NULL OR hex64(ticket_hash)),
 ticket_deadline_ms INTEGER CHECK(ticket_deadline_ms IS NULL OR ticket_deadline_ms BETWEEN 1 AND 9007199254740991),
 release_reserved INTEGER NOT NULL CHECK(release_reserved IN (0,1)),
 binding_id TEXT UNIQUE CHECK(binding_id IS NULL OR hex32(binding_id)),
 CHECK(
  (phase IN ('pending','confirming','cancelled') AND intent_id IS NULL AND ticket_hash IS NULL AND ticket_deadline_ms IS NULL AND release_reserved=0 AND binding_id IS NULL)
  OR (phase='issuing' AND intent_id IS NOT NULL AND ticket_hash IS NULL AND ticket_deadline_ms IS NULL AND release_reserved=0 AND binding_id IS NULL)
  OR (phase='issued' AND intent_id IS NOT NULL AND ticket_hash IS NOT NULL AND ticket_deadline_ms IS NOT NULL AND binding_id IS NULL)
  OR (phase='bound' AND intent_id IS NOT NULL AND ticket_hash IS NOT NULL AND ticket_deadline_ms IS NOT NULL AND release_reserved=1 AND binding_id IS NOT NULL)
 ),
 CHECK(phase!='cancelled' OR deny_requested=1)
) STRICT;
```

Required triggers, exact semantics (implementation uses these named statements, no conditional missing-object repair):

1. `stellar_nc_meta_nodelete_v3`: BEFORE DELETE meta, RAISE(ABORT,'consent history retained').
2. `stellar_nc_attempt_nodelete_v3`: BEFORE DELETE attempt, same refusal.
3. `stellar_nc_attempt_identity_v3`: BEFORE UPDATE attempt, ABORT if any challenge/profile/attachment/context/digest/Prepared/created field differs (`IS NOT` compares). These fields are immutable.
4. `stellar_nc_attempt_monotonic_v3`: BEFORE UPDATE attempt, ABORT on deny1->0, release1->0, changing a non-NULL intent/hash/deadline/binding, or phase transition outside SAME phase / pending->confirming|cancelled / confirming->issuing|cancelled / issuing->issued / issued->bound. Every positive phase advance requires OLD and NEW deny=0; bound requires release_reserved=1. Release0->1 requires OLD.phase=NEW.phase=issued and OLD/NEW deny=0 with unchanged intent/hash/deadline/binding. Same-phase updates cannot add/change an intent/hash/deadline/binding; pending insertion requires phase pending/deny0/all nullable fieldsNULL/release0. New field values arise only with the matching phase transition; nullable fields not assigned by that transition remain NULL. Negative cancellation cannot reset release or ticket fields.
5. `stellar_nc_attempt_count_v3`: AFTER INSERT attempt, update meta.retained_count=retained_count+1; CHECK above caps retention. Missing meta is rejected BEFORE INSERT by a sixth trigger, not silently ignored.
6. `stellar_nc_attempt_insert_v3`: BEFORE INSERT attempt, require exactly one meta row and fresh pending shape; otherwise ABORT.
7. `stellar_nc_meta_immutable_v3`: BEFORE UPDATE meta, ABORT on singleton/version/digest change or retained_count change except OLD+1 matching the actual current count(attempt). No API decrements or resets it.

No FK pragma is changed. Application verification checks bound-row joins explicitly. No DROP, DELETE, REPLACE, INSERT OR IGNORE or UPSERT is used for attempts. Unique challenge/attachment/intent/ticket/binding IDs are retained forever in this candidate. CHECK+triggers are integrity defenses against ordinary mistakes, not a security boundary against privileged TCB code dropping schema.

SQLite trigger-body DML does not allow schema-qualified target names: the count trigger's sole UPDATE uses its own main table name unqualified as required by SQLite. The trigger itself is explicitly created in main, all ordinary statements/catalog checks are main-qualified, no attached schemas/TEMP objects are allowed, and all other trigger bodies only RAISE. This narrow engine restriction is not a runtime fallback.

## Exact connection-local functions and ordering

All `_on` functions take caller-owned `sqlite3.Connection` and return **uncommitted domain data**, never a durable receipt/ACK. Exceptions/storage/commit outcomes propagate; no helper owns commit. No external I/O occurs inside them. The actual pinned SessionDB writer retries callback/commit BUSY/LOCKED and “no more rows” even after callback entry; its IOERR special case alone is not a no-retry guarantee. Therefore `once(callback)` captures a per-operation entered flag, sets it BEFORE first invocation, and on any re-entry raises non-SQLite JournalError(write_uncertain) without invoking work again. `write_once(db,fn)` calls db.\_execute_write(once(fn)); begin-lock retries before callback entry remain writer behavior. Fresh Ledger.bind uses a single `once`-wrapped `_on_bind` callback for the whole bind call. Do not recreate the guard for an automatic retry. Entry guards are memory safety, not durable receipts; retained DB phase/latch still governs restart/lost-ACK refusal.

## Crash/failure and recovery invariants

OneShotWriter delegates to the real SessionDB with a once-guard around the ENTIRE existing Ledger writer callback, before its first binding INSERT; the once-wrapped hook remains a second local fence. This is required because a commit-then-BUSY retry can otherwise reach the legacy binding INSERT before reaching the hook. The real SessionDB still owns locking/commit/rollback; Ledger.bind and current live host composition remain unchanged. This wrapper is data-only delegation, never DB/native authority.

The binding hook obtains now_ms from the current host clock INSIDE invocation after writer acquisition. Timestamp bounds do not establish provenance: fresh actual Ledger.bind composition is mandatory. Test an advancing fixture clock/lock wait: an earlier captured createdAt is accepted while the fresh transaction clock is before all deadlines; waiting past a deadline refuses and rolls back even though createdAt was earlier. Existing Ledger.bind need not change. Bound-row inspection allows subsequent legitimate spent counters/revocation, while preserving origin/options/owner and never treating it as new consent.

| Boundary                                        | Retained state and required refusal                                                                                           |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| migration DDL before commit                     | atomic rollback; partial/unknown pre-existing schema refuses rather than repairs                                              |
| reserve commit, ACK lost                        | profile/challenge/attachment latch remains; no new launch/prepare can bypass                                                  |
| begin commit, ACK lost                          | confirming remains; do not start OS prompt or repeat begin from row inspection                                                |
| issuing committed, before/after future approve  | issuing remains unknown regardless of ticket-hash absence; never infer definitely-not-issued                                  |
| ticket record commit, ACK lost                  | issued hash only; never reconstruct/reissue raw ticket                                                                        |
| release reserve committed, enqueue partial/lost | release1 retained; no retransmission; queued bytes may arrive but sticky deny still blocks bind                               |
| bind commit, ACK lost                           | bound journal+binding+owner committed together; consumer uncertain; no rebind/recovery endpoint                               |
| cancel wins                                     | deny cannot clear; no issue/release/bind may later succeed                                                                    |
| bind wins then cancel                           | same transaction domain revokes exact binding and reserves canonical cancellation obligations; no physical stop certification |
| error/IOERR/commit outcome unknown              | propagate; host/consumer retain local denial/uncertainty; no write callback retry after it starts                             |
| restart/new epoch/process/empty memory          | retained profile latch and IDs remain; no automatic expiration/retirement or re-enrollment                                    |

Negative cancellation may repeat on an already denied row to ensure revocation/obligations stay paid; it cannot produce a new positive transition, clear a fence, change identity or turn late/unknown issuance into successful rollback. Successful pre-issue cancellation still does not release the profile latch. DB data does not prove native window closure, user confirmation, host liveness, audible speech or cleanup.

## Primary transaction evidence
